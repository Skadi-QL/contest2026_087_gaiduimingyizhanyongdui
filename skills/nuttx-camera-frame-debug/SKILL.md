# NuttX V4L2 摄像头画面异常诊断

## 分层排除顺序（从最便宜的开始）

1. **跨端比对像素格式的取色代码。** 若图像经过多段处理（设备编码 / 服务器转码 /
   中继转发），把每一端的 RGB565→RGB 代码逐行比对：小端读法、5/6/5 位段、
   位扩展公式。**确认逐位相同**，才能排除字节序与位段问题，把注意力转向数据本身。
2. **看异常是否逐帧变化。**「每帧卷动量/错位量都不同」是**采集侧相位问题**的指纹；
   「每帧都一样」更可能是格式或配置错误。
3. **量化噪声性质**再决定治哪里（见下）。

## 画面卷动 / 彩色纹样：DMA 起始相位没对齐

**症状**：画面水平卷动一段。当卷动量是**奇数个字节**时，RGB565 的 2 字节配对整体
错位，R/G/B 位段全乱 → 表现为**偏蓝偏绿的彩色纹样**，且每帧形态不同；卷动量为偶数
时只是纯位移、颜色正常。

**为什么查不出来**：移位后的帧**自洽且字节完整** —— `vbuf.bytesused` 永远是完整帧
长，`V4L2_BUF_FLAG_ERROR` 也从不置位。设备端日志、中继日志、HTTP 状态全都正常，
**只能从画面看出来**。不要指望在协议层或日志层发现它。

**根因**：DMA 通道由 `start_capture` **异步**启动，而传感器处于**自由运行**状态
（传感器自己的 start_capture 往往是 no-op）。DMA 从传感器帧的任意相位开始写
`fb[]`，`fb[0..P)` 是上一帧的尾部，P 每次采集都不同；而完成回调无条件拷贝
`fb[0..fb_size)`，于是整幅图被**圆周移位 P 字节**。

**修法**（`arch/*/src/<chip>/<chip>_cam.c` 的 VSYNC 中断）：在**第一个 VSYNC** 里
把 DMA 通道从描述符链头重启一次——

1. 置 `DMA_INLINK_STOP` 停通道；
2. 有界轮询等 `DMA_INLINK_PARK` 置位；
3. 复位 async FIFO（否则残留字节会被 prepend，留下残余位移）；
4. 重新起通道，让新帧正好落在 `fb[0]`。

VSYNC 之后有**垂直消隐**，重对齐能在第一个有效像素到来前完成。

**注意**：若驱动在 `capturing = true` 之后才注入人工 VSYNC 边沿，那个边沿会被当成
第一次 VSYNC，导致重对齐早跑一帧 —— 把 `capturing = true` 移到注入之后。

## 噪点：先判断是传感器还是编码

**放大看颗粒形态**（`Image.crop(...).resize(..., Image.NEAREST)`）：

- 颗粒是 **2×2 小块** → 色度子采样（JPEG 4:2:0）。可量化验证：转 YCbCr，比较水平
  相邻像素差的「偶数起」与「奇数起」均值，比值明显 >1 即为子采样。
  治法：编码时 `subsampling=0`（4:4:4）。
- 颗粒是**逐像素散粒** → 传感器噪声。

**分通道量化**：分别算 Y / Cb / Cr 的相邻像素平均差。亮度差远大于色度差 ⇒ 是
**亮度噪声**（传感器增益），不是编码造成的色斑。

**常见根因**：驱动**只配置 SoC 的摄像头外设（DMA/时钟/GPIO），没有传感器寄存器
初始化表**，传感器跑上电默认值，暗光下自动增益拉满。Espressif 官方 esp-camera 会
下发调好的寄存器表（含降噪开关与增益上限）。

**治法按性价比**：① 加照明；② 接收端做降噪 / 多帧平均（不动固件）；③ 在驱动里补
传感器寄存器表（内核改动，风险最高）。

## 视觉陷阱：分辨率会骗人

点采样降采样**不会降低**单像素噪声，但降分辨率后的图在网页上被放大显示，视觉上被
平滑了，容易误判为「以前更干净」。评估前先确认对比的是同等条件下的原图。

## 验证改动是否真的生效

不要用 md5（固件里嵌了版本/日期，每次构建都变）。用反汇编比对目标函数的指令数：

```bash
xtensa-esp32s3-elf-objdump -d nuttx | awk '/<cam_interrupt>:/,/^$/' | wc -l
```
